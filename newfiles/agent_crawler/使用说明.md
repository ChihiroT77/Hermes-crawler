# Hermes 智能体调用说明（MediaCrawler 封装层）

> 目标：**一句话 → 我执行**。AI 助手（或你本人）只需发出一条命令，封装层负责
> 参数校验、登录预检、冲突检测、运行监控、数量对账、完整性抽查、归档与报告。
> 对 MediaCrawler 源码**零修改**（本目录与 `tasks/` 归档目录独立于项目代码）。

---

## 1. 快速开始

### 先装上（只需一次）

拿到的是「成品插件包」那个文件夹的话，**双击里面的「一键安装.bat」**，其余什么都不用做：

- 它会自己找 MediaCrawler 的位置（找不到会问你要路径，也可以把文件夹直接拖到 bat 上）；
- 打补丁前先逐条"试打"，**有一条打不上就整体停下，你的项目一个字都不会被改**；
- 装完会自检依赖、并打印装好的版本号；
- **以后升级也双击同一个文件**——它认得"以前装过"，会自动只覆盖插件部分。

想先看一眼、不落盘：`powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1 -DryRun`。

装没装上、装的是哪一版，随时可以问：

```bash
.venv\Scripts\python.exe agent_crawler\agent_crawl.py version
```

### 开始用

```bash
# 在项目根目录（MediaCrawler 所在目录）执行
.venv\Scripts\python.exe agent_crawler\agent_crawl.py run -p bili -k "人工智能" -n 20
```

平台支持中文别名：`抖音/快手/B站/微博/贴吧/知乎`。

> **关于小红书**：反爬是七个平台里最狠的（强验证码，人工操作也常过不去）。我们**不再推荐、
> 也不保证能跑通**，要稳定出数据请用上面前六个平台。代码没删，你想试还是能试，
> 但别指望它；用 `estimate` 或 `run` 指定 `-p xhs` 时，程序会主动警告一次。

**免扫码（推荐先做一次）**：在桌面 Edge 里把要采的平台登录好，然后**双击
`agent_crawler\安装免扫码插件.bat`**，按窗口里的三步提示操作一次即可。
之后扩展会在你登录后自动把登录票导出到"下载"文件夹，爬虫开跑前自动导入——不用反复扫码。
需要重新扫码的情形用 `login` 子命令。完整说明见 `agent_crawler\免扫码说明.txt`。

### AI 助手调用约定

**首选：加 `--json`。** `run / batch / status / export / estimate / cancel / login / defaults / version`
九条命令都支持。加上它之后，
屏幕上的人类进度会改到旁路（stderr），**stdout 只剩一段固定结构的 JSON**，字段名永远不变：

```bash
agent_crawl.py run -p bili -k 人工智能 -n 50 --json
```

固定字段（缺一个都不行，顺序不变）：`ok` 成没成｜`status` 三态｜`reason` 原因原话｜
`reason_kind` 原因大类（`not_logged_in` / `no_data` / `network` / `other`）｜`reason_kind_label`
大类中文名｜`advice` 该怎么办｜`platform`｜`type`｜`keywords`｜`count_per_keyword`｜`format`｜
`requested`｜`contents`｜`comments`｜`attempt` 第几次跑成｜`retries` 中间重试几次｜
`max_attempts` 最多允许几次｜`empty_result`｜`exit_code`｜`qr_prompted`｜`duration_s`｜
`task_dir`｜`report`｜`log_path`｜`primary_file`｜`files`｜`spot_check` 抽查结果。

`batch` 的 JSON 是 `{ok,status,total,ok_count,failed_by_kind,tasks[]}`，每个任务一条同样结构。
`status --json` 返回环境/锁/进度/最近任务；`status --task 名字 --json` 返回单个任务详情
（含 `attempts[]` 每次尝试各拿到多少条、日志路径）。

不改代码也读得下去，但需要自己从文字里抠数字；能用 `--json` 就尽量用。

1. **调用前**无需人工确认参数——封装层会自行校验并拒绝非法请求。
2. **运行中**输出逐行实时转发（`  | ` 前缀），进度真实，绝不假报。
3. **结束后**解析最后一行机器可读结果：

```
RESULT: name=任务名 status=成功|部分完成|失败|预检失败 contents=实际/请求 comments=N file=绝对路径
```

4. **退出码**：`0`=成功（数量达标）｜`2`=部分完成或已取消（有数据但不足额，或者你喊了停）｜`1`=失败/预检未通过｜`130`=用户中断（Ctrl+C）。
   ⚠️ 若经 AI 助手的后台通道（DSH background job）发起，通道会把非零退出码归一化成 `1`，
   此时**以 `RESULT:` 行的 `status=` 为准**，不要依赖 job 上报的退出码。

### 三态状态的含义

| 状态 | 判定 | 处置建议 |
|---|---|---|
| ✅ 成功 | 实际条数 ≥ 请求条数 | 无需处理 |
| 🟡 部分完成 | 有产出但不足额（平台结果不足/风控限量/提前结束） | 数据可用；如需补量可加关键词或改天重试 |
| ❌ 失败 | 零产出（登录/风控/网络/浏览器/超时） | 按报告中的"原因"行处置，见故障排查表 |
| 🚫 已取消 | 你喊了停（`cancel`），一条数据也没拿到 | 不是故障；想跑就重新发起 |

**零产出有两种，别混**：一种是**跑挂了**（登录/风控/网络/浏览器/超时），另一种是
**跑通了但平台就是没内容**——进程正常退出、exit=0、平台接口明确返回空。后者不是故障，
不会自动重试；报告"原因"会写成 `平台返回 0 条（…，关键词「XXX」）；证据日志：<日志原文那行>`，
能直接看出是哪个关键词空、平台自己是怎么说的。若所有关键词全空，还会补一句
`N 个关键词全部为空 → 更像是登录票降级或被风控限流`，此时先 login 或换个关键词再试。

**请求条数基数**：`search` = 每关键词数量 × 关键词数；`detail` = 指定 ID 数；`creator` = 创作者数。

**重试了没有、试了几次**：报告里多一行 `尝试次数`，说人话的样子是
「第 1 次就出结果（一次过，没重试；最多允许跑 3 次）」或「第 3 次才出结果｜中间重试了 2 次（已到重试上限）」。
`status` 历史和 `--json` 里也有（`attempt` / `retries` / `max_attempts`）。

**失败原因归成四类，别混**：

| `reason_kind` | 大白话 | 该怎么办 |
|---|---|---|
| `not_logged_in` | 没登录（票过期、码没扫上） | 先补票再跑，不补票重跑结果一样 |
| `no_data` | 平台没内容（跑通了，平台接口确实空） | 不是故障，别重跑，换关键词 |
| `network` | 网络或接口出问题（断网/风控/超时/浏览器） | 等几分钟重试或换网络；先 `status` 看有没有残留浏览器 |
| `other` | 不是爬取失败（参数写错/本机有任务占着/批量文件读不了/你按了 Ctrl+C 或喊了停） | 按提示改，不用查网络和登录 |

报告里会同时给出 `问题归类` 和 `该怎么办` 两行；`--json` 模式是 `reason_kind` + `advice` 两个字段。

## 2. 子命令与参数

### `run` — 单任务爬取（核心入口）

| 参数 | 说明 | 默认 |
|---|---|---|
| `-p / --platform` | 平台：bili/zhihu/wb/dy/tieba/ks（支持中文别名）。**xhs（小红书）已不推荐**，见下 | 必填 |
| `-k / --keywords` | 关键词，英文逗号分隔，最多 10 个 | 必填 |
| `-n / --count` | **每个关键词**爬取条数，1~300 | 记忆值(初始20) |
| `-f / --format` | json / jsonl / csv / excel | 记忆值(初始jsonl) |
| `-t / --type` | search / detail / creator | search |
| `--specified-id` | detail 类型必填：内容 ID，逗号分隔 | — |
| `--creator-id` | creator 类型必填：创作者 ID，逗号分隔 | — |
| `--name` | 任务名（归档目录名 = `任务名_平台_日期`） | 第一个关键词 |
| `--comments / --no-comments` | 是否抓评论 | 开 |
| `--max-comments` | 每条内容的评论数上限 1~100 | 10 |
| `--media / --no-media` | 是否下载媒体文件 | 关 |
| `--headless / --no-headless` | 无头模式（可见窗口反爬更稳） | 可见窗口 |
| `--retries` | 基础设施类错误（网络/浏览器/超时）自动重试 0~3 次 | 1 |
| `--timeout-min` | 超时分钟（默认自动：10 + 数量/10，开评论再加 数量×每条评论上限/60，上限 180） | 自动 |
| `--wait-lock` | 本机已有任务在跑时，最多排队等几分钟（0 = 直接退出，不抢） | 0 |
| `--probe / --no-probe` | 开跑前先探一次票（泛词取 1 条真数据）。**都不写=自动**：dy/ks/xhs + 长任务自动开 | 自动 |
| `--start` | 从第几页开始抓（续跑用；不传=第 1 页）。注意它把抓取窗口整体往后平移，不是"少抓" | — |
| `--detach` | **甩到后台跑**：命令立刻返回，任务自己接着干，关掉窗口也不影响 | 关 |
| `--passthrough` | 透传给 main.py 的额外原始参数（高级逃生口） | — |

#### `--probe` 是什么、什么时候该开

抖音/快手/小红书的票在预检时只能验"文件在不在"（平台接口要签名，本机问不了），票过期
往往要跑到一半才暴露——夜里第 3 小时才发现白跑。加 `--probe` 就先花 20~40 秒冷启动
浏览器、用泛词真取 1 条：

- 成功 → 预检里多一行 `探针：取到 1 条数据 ✓（票可用，探测词「新闻」）`，然后正常开跑。
- 失败 → **停在预检**（状态"预检失败"，不产生任务目录），结论会区分三种原因：
  票失效/被风控降级（带日志线索）、弹了扫码窗口（补票命令直接给出）、超时
  （浏览器起不来或网络卡死，不是票的问题）。
- 探针数据落在 `agent_crawler\_probe\`，成功即删，**不进 `tasks\`、不写历史**。
- 探针在**拿到运行锁之后**才执行（否则等于和别人抢浏览器）。
- `batch` 只在队列开头探一次，后面的任务沿用结论（同一把锁、同一份票）。

**现在是三态，不是"开/关"两态**：

| 你怎么写 | 效果 |
|---|---|
| 什么都不写 | **自动判断**：本机验不了票的平台（dy/ks/xhs）**且**这次总量 ≥ 100 条 → 自动开；其它情况不开 |
| `--probe` | 一定探（想探就探，哪怕平台能验票、哪怕只有 20 条） |
| `--no-probe` | 一定不探（自动判断觉得该开也不开） |

自动开的时候，预检会多打印一行原因，比如："自动开探针：抖音 这台机器验不了登录票的
有效性，这次又算长任务（共 1200 条）……不想探可以加 --no-probe"；`--json` 里对应
`probe` / `probe_auto` / `probe_note` 三个字段。

为什么这么分：bili/微博/贴吧/知乎能真问一句"票还有效吗"，不必为了它多花半分钟；
dy/ks/xhs 问不了，而小任务（几十条）失败了重跑一次就完事，也不值得等冷启动。
**登录任务自己不做探针**——它本来就是在测登录。

探针选的是"泛词搜索取 1 条"而不是"抓固定内容 ID"：ID 会失效（删稿/转私密），
一失效就和票失效分不开，还得长期维护 ID 表；泛词失败只可能是票/风控/网络。

**默认值记忆**：任务**成功后**，本次使用的 count/format/type/comments/max_comments/media/headless
会写回 `state.json`，下次调用省略即沿用；`defaults` 子命令可随时查看/修改。

#### 长任务三件套：先估、再甩后台、随时能喊停

爬几百条、上千条评论是要跑几个小时的。这三件事就是为长任务准备的，都是新加的。

**一、先估一下（`estimate`）**

跟 `run` 收一模一样的参数，但**它不真跑**——不起浏览器、不发一个网络请求，只算给你看
大概要多久、能拿到多少条。

```bash
agent_crawl.py estimate -p zhihu -k 美食 -n 20 --max-comments 50
```

有历史就有依据：它翻自己以前的账本（`state.json`），挑同一个平台同类任务的实际耗时
反推，并明确告诉你"按本机 2 次同平台实测，平均每条内容 9.6 秒（含评论在内）"，
再给个把握度（高/中/低）。从没在某个平台跑过，就只能按经验粗估，它会直接说
"差不多是这么个数，别当准数"。

参数写错了（比如条数超过 300）当场就报错，不用等跑一半才发现。

**二、甩到后台（`run --detach`）**

不加的话，命令得一直挂着：窗口关了、断网了、电脑睡眠，任务就断了。加 `--detach`
就是"我把活交出去，你忙你的"：

```bash
agent_crawl.py run -p zhihu -k 美食 -n 100 --max-comments 200 --detach
```

它立刻返回一段信息（任务名、进程号、日志在哪、怎么查进度、怎么喊停），然后你自己
该干嘛干嘛。关掉终端窗口也不影响它继续跑。

之后随时查进度还是老命令：`agent_crawl.py status`（或 `status --task 任务名` 只看这一个）。

**三、随时喊停（`cancel`）**

```bash
agent_crawl.py cancel                 # 喊停，等最多 30 秒看它收没收工
agent_crawl.py cancel --wait 60       # 最多等 60 秒
```

它不是"一刀砍死"。喊停只是递一张纸条，干活的那个进程每 2 秒看一眼，看见了就自己
走正常收尾流程：停止翻页、关浏览器、写报告、把锁摘掉。**已经落盘的数据一条不丢**，
状态会如实记成 `部分完成`（有数据）或 `已取消`（一条没拿到）。

这样设计是因为硬砍进程可能把浏览器砍坏、把登录态搞丢，得不偿失。

三个小提醒：

- 喊停之后**不会自动重试**，就是停在那儿了。
- 上一次任务被强杀留下的旧纸条，下次开跑前会自动清掉，不会误伤新任务。
- `cancel` 发现"锁还在但进程其实已经死了"（残留锁），会顺手清理掉并告诉你，不算出错。

#### 断点续跑（`resume`）：接着上次的进度抓

昨晚跑了 3 个词，跑到第 2 个词时票过期／电脑重启／你喊停了。不想整个重跑一遍
（旧数据浪费、重复数据还得手工去重），就用 `resume`：

```bash
agent_crawl.py resume --task 考研_zhihu
agent_crawl.py resume --task 考研_zhihu --detach      # 甩后台（推荐）
agent_crawl.py resume --task 考研_zhihu --from-scratch # 不管进度，全从第 1 页重抓
```

**它干的三件事，顺序不能反**：

1. **只读磁盘先算账**（不联网、不起浏览器）：旧任务里每个关键词已经拿到多少条、
   上次翻到第几页，全算清楚。够数的词直接标"已完成"，不白跑。
2. **逐词补抓**：只对没够数的词再跑一次，从"上次停下的下一页"接着抓。
3. **按 ID 去重合并**：旧的 + 新的按内容 ID 合并（抖音 aweme_id、B站/快手 video_id、
   微博/贴吧/小红书 note_id、知乎 content_id，评论统一 comment_id），重复的丢掉。

**产出是一个新目录** `<原名>_续跑_平台_日期`，旧的 `tasks\` 目录一个字节不动
（想核对、想回退都行）。

几个必须知道的限制：

- **只支持 jsonl / json / csv**。旧任务要是有 `.xlsx`，直接拒绝并提示你换格式——
  Excel 是整份覆盖写的，拿它做合并早晚出错。
- **只支持搜索任务**（`type=search`）。detail / creator 没法判断"抓到哪一步"，不支持。
- 原码的 `--start` 是个**全局单值**，所以只能一个关键词一个关键词串行补，不能一批
  同时从不同页开始。
- `--start` 的真实语义是**把抓取窗口往后平移**，不是"少抓"。比如 B 站要 100 条、
  从第 3 页起 → 它跑第 3~7 页共 5 页，还是 100 条。所以能不能真拿到新东西，取决于
  这个关键词后面还有没有页——平台已经没更多了，续跑也只能补到个位数。
- 页码从哪来：抖音/B站/微博/小红书日志里有 `page: N` 这种行，能精确定位到第几页；
  快手/贴吧/知乎日志里只有 `Skip page: N`，定位不到，就按"已有条数 ÷ 每页条数"
  保守推算——这一点会明写在结果的 `page_basis` 里，不假装精确。
- 续跑时票已经过期？照样会先预检，不过就停在预检失败，不会把旧数据弄坏。

其它开关：`--attempt N`（旧任务重试过好几次，指定读第几次的数据；默认取编号最大的
那次）、`-n`（这次按多少条算，默认沿用旧任务当时的设置）、`--probe/--no-probe`、
`--wait-lock`、`--timeout-min`、`--json`、`--detach`。

状态词：`续跑完成`（都够数了）/ `部分完成`（还差一些）/ `无事可做`（旧任务本来就够了）/
`已取消` / `失败`。退出码 0=完成或无事可做、2=部分完成或被取消、1=出错。

### `mcp_server.py` — 给 AI 用的标准工具接口（可选）

上面的子命令是给人敲的。如果想让支持 MCP 的 AI 客户端（各种 Agent 工具）**直接调用**
爬虫，就在客户端里登记一个 MCP 服务，指向本目录的 `mcp_server.py`：

```json
{
  "mcpServers": {
    "Hermes": {
      "command": "%MC_ROOT%\\.venv\\Scripts\\python.exe",
      "args": ["%MC_ROOT%\\agent_crawler\\mcp_server.py"]
    }
  }
}
```

登记完 AI 会看到十个工具：`crawl_start`（开跑，默认后台）、`crawl_wait`（**启动后接着等，跑完一次性给结果**）、
`crawl_status`（查进度）、`crawl_cancel`（喊停）、`crawl_estimate`（预估）、`crawl_export`（导出 Excel）、
`crawl_batch`（批量队列，默认后台）、`crawl_resume`（断点续跑，默认后台）、
`crawl_login_check`（只查登录态，**不会替你登录**——登录必须有人在场）、
`crawl_defaults`（看/改默认参数）。
它们底下跑的还是上面那些命令，规则、校验、状态全是同一套，不存在"两套逻辑"。

> 为什么有 `crawl_wait`：`crawl_start` 是「点火就返回」，AI 拿到"已启动"这一轮对话就结束了，
> 用户只看到一句话，不知道到底成没成。`crawl_wait` 把"等"这一步放进工具里：AI 阻塞等，
> 跑完直接拿到"成了没、几条、文件在哪"，一句话交代完。

想自己先验一下有没有毛病（不装客户端也能测）：

```bash
.venv\Scripts\python.exe agent_crawler\mcp_server.py --selftest
```

会打印十个工具的清单，并真调一次 `estimate` 和 `status` 看返回是否正常。


### `batch` — 批量任务队列

```bash
agent_crawl.py batch --file 批量任务示例.json
```

JSON 数组，每项字段与 run 参数同名（`platform`、`keywords`、`count`…），顺序执行、
任务间隔 10 秒、结束输出汇总表。单项失败不影响后续任务。

整条队列**共用一把运行锁**：开头抢一次，队列结束才摘下。所以中途每一项不会再去
"查有没有别人在跑"（那时唯一在跑的就是自己），也不会互相误关浏览器。

队列里有写错的项（平台名不支持、条数超范围）不会让整条队列断掉：那一条记为
"预检失败"并写明原因，后面的照跑。汇总表里能看到是哪一条出的问题。

**长队列建议甩后台**（加 `--detach`）。一条队列十来个任务、每个几百条，跑几小时很正常：

```bash
agent_crawl.py batch --file 批量任务.json --detach
```

它会立刻返回，进程号和日志路径都告诉你；查进度还是 `status`（整条队列不指定 `--task`），
喊停还是 `cancel`。想让队列留在本机慢慢跑、自己关电脑走人，就用这个。

### `login` — 触发平台扫码登录

```bash
agent_crawl.py login -p zhihu
```

- **多数情况你不需要跑这个**：先在桌面 Edge 登录好，装一次
  `agent_crawler\edge_cookie_ext` 扩展，它会把票自动导出（`mc_cookies_auto_*.json`），
  爬虫开跑前会自动导入。详见 `agent_crawler\免扫码说明.txt`。
- 启动前**先提示**把手机 App 准备好——二维码窗口只等约 20 秒。
- 登录成功后登录态保存在 `browser_data/cdp_{平台}_user_data_dir/`，之后 run 无需再扫码。
- 已登录平台执行会直接告知并退出，不做多余动作。

### `status` — 环境巡检

显示：**运行锁现状**（谁在跑、跑了多久、是不是失效残留）/ 正在运行的爬虫进程 /
残留爬虫浏览器 / 最近 10 条任务历史。

进程那一栏**按任务归并**：一次 `run` 实际上会看到 4 个 python 进程（venv 启动器 →
真进程 → TIME_SHIM 壳 → 真进程），它们是一条链上的同一件事。`status` 会顺着父 pid
往上找最顶上的那个爬虫进程当作"头进程"，把子孙都挂在它名下，显示成
`有 N 个爬虫任务正在运行（共 M 个进程…）`。所以看到"4 个进程"别以为并发了 4 个任务，
**任务数看 N，进程数看 M**。真有两拨人在跑，N 才会是 2。

**顺便估一下还要多久**：锁没失效、人还在跑时，`status` 会多打一行 `↳ 进度估算…`，
比如 `内容 16/60 条（27%），已跑 2分51秒，按当前速度约还需 5分46秒`。

- 数字是**数磁盘上 jsonl 的行数**得来的，实时、不需要问爬虫进程，也不改 `run.lock`；
- 速率只从"第一条数据落盘"算起：浏览器冷启动那 30~60 秒不是采集速度，算进去会把
  剩余时间估成两倍以上；
- 门槛：跑不到 90 秒、或数据不足 3 条，就只说已落盘多少、不谈剩余时间；
- 采够了会直接说 `内容已够 60/60 条（100%），正在收尾` / `正在采评论`；
- **是线性外推，仅供参考**。实测一个 60 条的任务：中途 2分51秒 时估还需 5分46秒，
  实际全程 7分15秒（估的总时长偏高约 19%）。平台的翻页/限速会让速度前后不一致；
- 批量队列跑的时候不估（任务名一直在换，估出来是错的）。

**只看某一个任务**：加 `--task 任务名`（名字可以只给片段，也可以给 `tasks\` 下的路径），
一条命令说清六件事：当初怎么跑的 / 跑到哪了（几条/共几条、百分比）/ 现在什么状态 /
重试情况 / 每次尝试各拿到多少条、日志在哪 / 文字报告路径。老任务没进历史记录的，
会从它的报告文件里把状态和参数读回来。

```bash
agent_crawl.py status --task 分片dyP02
agent_crawl.py status --task 分片dyP02 --json
```

### `defaults` — 查看/设置默认参数

```bash
agent_crawl.py defaults                    # 查看
agent_crawl.py defaults --set count=30 format=excel
```

### `version` — 装了哪一版

```bash
agent_crawl.py version                     # 人看
agent_crawl.py version --json              # 给 AI / 脚本看
```

`mcp_server.py` 在不在）。排查"我装的到底是不是最新的"就看这个——别靠文件日期猜。

### `export` — 把已采任务导出成交付用 Excel（只读磁盘，可在别人跑任务时用）

```bash
agent_crawl.py export --task 分片dyP02                       # 名字可以只给片段
agent_crawl.py export --task "tasks\某任务"                  # 也可以给完整路径
agent_crawl.py export --task 分片dyP02 --kinds contents,comments,creators
agent_crawl.py export --task 分片dyP02 --attempt 2 --out D:\交付\抖音.xlsx
```

产物默认落在 `agent_crawler\exports\{任务名}_{时间戳}.xlsx`，第一张表是「口径说明」，
后面每类数据一张表（内容 / 评论 / 创作者），**再往后每类多一张「统一格式」表**
（`统一格式` / `统一格式_评论`）。不想加统一页就加 `--no-unified`。

**统一格式页是什么**：七个平台列名不一样（同是点赞，有 `liked_count`、`like_count`、
`voteup_count`），横向拼表要写一堆对照。统一页就是照着搬的一份副本，列名和顺序固定：

| 内容统一页（9 列） | 评论统一页（9 列） |
|---|---|
| 内容ID / 标题 / 正文 / 作者昵称 / 发布时间 / 点赞数 / 评论数 / 链接 / 关键词 | 评论ID / 所属内容ID / 父评论ID / 评论正文 / 评论者昵称 / 评论时间 / 点赞数 / 子评论数 / IP属地 |

三条原则：**原始页一个字不动**（统一页只是副本，改数据请在副本上改）；**对不上的列留空，
绝不猜**（微博没标题列就空着，不拿正文前几个字顶）；**没核对过的会逐表说明**——
本机真跑过、对着真实表头核过列名的情况是：

| 平台 | 内容表 | 评论表 |
|---|---|---|
| 抖音 / 微博 / B站 / 贴吧 | 已核对 | 已核对 |
| 知乎 | 已核对（18 条真实数据） | 已核对（1126 条真实评论） |
| 快手 | 已核对（20 条真实数据） | 未核对（本机没有快手评论数据） |
| 小红书 | 未核对（按源码字段推断） | 未核对（按源码字段推断） |

没核对的那张表，口径页会单独写一行「某平台某表本机没有真实产出核对过列名，
第一次用请抽查两行」。这是按“平台+表”逐张标的，不是笼统说整家平台都对过。

快手补一句：正式登录态下快手会要人机验证（搜索接口回 `400002`），爬虫过不去，
所以快手这块**暂时搁置**，不是没做。没登录的匿名状态下能采到东西，但数据会少。

时间统一成 `2026-10-10 22:40:01` 这种可读格式（原本是秒或毫秒时间戳）；ID 一律按文本存，
不会被 Excel 变成科学计数法。

**只搬不改**：不排序、不去重、不改写正文、不加统计列。派生内容只有四样，且都写在
口径页的「转换统计」里，条数可核：

| 派生物 | 为什么 |
|---|---|
| 末列 `来源文件` | 说明每行来自哪个 jsonl/xlsx |
| 列表/字典字段转 JSON 文本 | Excel 一个格存不了列表（如话题标签、图片列表） |
| 长数字（ID/哈希/原始时间戳）按文本存 | 否则 Excel 会显示成 `1.7896E+18`，19 位 ID 直接丢精度 |
| 去掉 Excel 存不了的控制字符 | emoji 残缺残留（0x08 之类），不去掉 openpyxl 会拒收整格；源 jsonl 原值完好 |

超 32767 字符的正文截到 32000 并计数申报（硬性单元格上限）。

导出后会**读回自己写的文件再校验一遍**：冻结首行、自动筛选、长数字列确实是文本
（`data_type=='s'`）、sheet 名与行数对得上、统一页表头与约定列名逐一对应、
**统一页行数必须等于原始页行数**。校验不过就返回 2，不会假报成功。

口径页会写清：任务名/平台/关键词/**采集时段**（`last_modify_ts` 最早~最晚，是写库
时刻，不是发布时间）/请求与实际条数/每个源文件绝对路径/**发布时间列是秒还是毫秒**
/已知缺失（哪类没采集）/三项自查（关键列空值、1970 或未来时间、行数与源文件对账）。

> 缺就是缺：某类没采到就标「未采集」，**绝不用别的指标顶替**（比如没抓评论就不该
> 出现"评论数=转发数"）。想改数据结构请自己另存一份改，别在导出件上动刀。

## 3. 输出与归档结构

```
tasks\{任务名}_{平台}_{YYYYMMDD}\                   ← 每次任务独立目录（重名自动 _r2 后缀）
├── params.json                                       ← 这次请求的参数快照（status 靠它算进度）
├── attempt_1\{平台}\{格式}\search_contents_*.jsonl   ← 爬虫原始输出（每次尝试隔离）
├── run_attempt_1.log                                 ← 该次尝试的完整子进程日志
└── report.md                                         ← 本次任务报告（人读）
```

- 多次重试产生 `attempt_2\`、`run_attempt_2.log`…，互不覆盖。
- `params.json` 是任务开跑时就写下的（平台/类型/关键词/条数/请求总数/评论开关），
  跑的过程中 `status` 只能靠它知道"这次一共要多少条"，事后也不用翻 `state.json`。
- `state.json`（同目录）保存默认值与最近 100 条历史。

## 4. 预检流程（不出错的第一道闸）

按顺序执行，任一环不通过立即失败并给出明确原因与处置建议：

1. **抢运行锁（`agent_crawler\run.lock`）**：这是"门口挂牌"。牌子上写着谁在跑、
   跑哪个平台、什么任务、几点开跑，并且每 30 秒刷新一次（心跳）。
   牌子被活人占着 → 拒绝，**绝不抢、绝不杀别人的任务**（`--wait-lock` 可排队等）。
   占牌进程已死，或牌子 30 分钟没刷新 → 判定为失效残留，自动接管。
2. **参数校验**：平台/数量/格式/类型专属参数/关键词。
3. **进程冲突检测**：找 `main.py` / `agent_crawl.py` 的爬虫进程，**排除自己和自己
   的所有父进程**（venv 的 python.exe 会在外面再套一层同命令行的进程，不排除会把
   自己认成"别人"）。同一条启动链上的多个进程会先归并成 1 个任务再报数，所以报错里
   的"1 个任务 / 共 4 个进程"指的就是一个人跑的一个任务。**只读命令不算冲突**：
   `status` / `defaults` / `version` / `export` / `estimate` 不占浏览器，边等边查进度
   不会被误拦（1.11.1 起）；`run` / `batch` / `login` / `resume` / `cancel` 和原始
   `main.py` 照旧算。发现别人在跑 → 拒绝（CDP 端口 9222 与浏览器 profile 无法并发）。
4. **残留浏览器清理**：发现上次遗留的爬虫 Edge → **优雅关闭**（绝不强杀，
   防登录态 profile 损坏）；关不掉则请你手动处理。
5. **登录预检**：先看有没有 profile，再**真的拿 cookie 去平台接口问一句**
   （不是只看文件在不在）；验不了的平台（接口要签名）按"有票就算过"。
   没过时先自动把 Edge 扩展最新导出的票导进来再验一次；还不行才报"未登录"并给三条处置。
   **绝不会跑到一半才弹二维码**（若运行中 cookie 过期，会实时弹出醒目扫码提示——
   窗口约 20 秒）。

## 5. 故障排查表

| 报告原因/现象 | 根因 | 处置 |
|---|---|---|
| `本机已有任务在跑，同一浏览器/端口不能并发` | 别的任务（可能来自另一个会话/终端）正握着运行锁 | 等它跑完；想排队就加 `--wait-lock 10`；确认人已不在可手动删 `agent_crawler\run.lock` 再重试 |
| `检测到已有爬虫进程正在运行` | 有爬虫进程活着但没挂牌（旧版本启动的，或锁被删了） | 等它结束；确认无用后手动结束再重试 |
| `未登录：未找到 …user_data_dir` | 该平台从未登录过 | 先 `agent_crawl.py login -p 平台`（扫码窗口 10 分钟） |
| `需要人工操作：请扫码`（运行中出现） | cookie 过期 | 在弹出的浏览器里扫码即可继续；或 Ctrl+C 后先 login 再重跑 |
| `登录未完成（未扫码/二维码超时）`、`登录未完成（等满约 10 分钟没扫上码…）` | 错过扫码窗口或票已过期 | 报告里会给出三条补票命令（Edge 扩展导出 / 贴 cURL / 再扫一次），照抄一条即可 |
| `平台返回 0 条（…）` | **不是故障**：跑通了，平台接口确实返回空 | 先确认关键词本身有没有内容；所有关键词全空则优先怀疑登录票降级/风控，先 login 或换词。不会自动重试 |
| `平台风控/反爬拦截` | 触发平台风控（403/412/频率限制） | 等几小时；降数量、降并发、改用可见窗口 |
| `平台实际返回 N 条 < 请求 M 条` | 平台本身结果不足或限量 | 正常现象，数据可用；补量可加关键词 |
| `浏览器异常/启动失败`、`网络异常`、`超时` | 基础设施问题 | **自动重试**（`--retries` 控制，默认 1 次） |
| Excel 输出损坏/警告 | 导出时文件被 Excel 打开占用 | 关闭 Excel 后重跑 |
| 想存 MySQL/SQLite 等数据库 | 封装层只管文件格式 | 用 `--passthrough` 或直接跑 `main.py`（改 config） |
| 结果条数比预期少一半以上 | `count` 是**每关键词**条数；多关键词 = count×词数 | 看报告"数量对账"行的请求基数 |
| 报告写 `已取消（人为喊停…）` | 你（或 AI）跑了 `cancel` | 不是故障；想要数据就重新发起一次 |
| `cancel` 说"没人在跑" | 任务已经结束了（可能刚好收工） | 用 `status` 看一眼就好 |

## 6. 安全边界（设计承诺）

- **零侵入**：不改 MediaCrawler 任何源码、配置；升级项目不影响本层。
- **不强杀浏览器**：爬虫 Edge 一律优雅关闭（保登录态）。超时的 python 子进程发
  CTRL_BREAK 停止信号（实测：MediaCrawler 未注册 SIGBREAK 处理器，Windows 会直接
  终结进程，不走其收尾钩子——但 jsonl 逐行落盘故数据完整；Excel 汇总表仅完整跑完
  的任务生成，超时任务主文件回落 jsonl；残留浏览器由封装层安全网 WM_CLOSE 清理）；
  20 秒不退出才强杀进程树。
- **显式 --timeout-min 如实生效**：自动公式才做 [3,180] 钳制；显式指定（含 <3 分钟）
  只受全局上限 180 保护，短超时演练可用。
- **不并发**：同一时间只允许一个爬虫任务。靠 `run.lock` 这一块"门口牌子"保证：
  后来者只会被拒绝或排队（`--wait-lock`），**不会去关别人正在跑的浏览器**。
  牌子每 30 秒刷新；进程已死或 30 分钟没刷新的牌子视为失效残留，可被接管。
- **数据不撒谎**：状态三态如实反映缺口；抽样 3 条做完整性抽查
  （标题/内容非空、作者字段存在（脱敏值算通过）、链接合法）。
- **喊停也是优雅的**：`cancel` 只递纸条，由干活进程自己收尾（停翻页 → 关浏览器 → 写报告 →
  摘牌），已落盘数据全部保留；绝不为了"立刻停"去硬砍浏览器。
- **日志全量留存**：每次尝试的完整子进程输出都在任务目录，可追溯。

## 7. 已知限制

- 登录预检**不是**只看文件在不在：有 profile 就会真拿 cookie 去平台接口问一句；
  但接口要签名的平台（抖音/小红书等）本机验不了，只能按"有票就算过"处理——
  这类平台的登录态是否还有效，只有真跑起来才知道（过期会在运行时弹扫码）。
- 退出码/`RESULT:` 只管文件产出，不判断数据质量（是否重复、是否跑偏）。
- 数据库类输出格式（db/mysql/sqlite）不在封装层职责内，请用 `--passthrough` 或原生 main.py。
- 同平台深度风控（如 xhs 强验证码）无法自动绕过，报告会如实标注。
- `estimate` 的预估**不是承诺**：某个平台从没跑过就只能按经验粗估；跑过之后会按本机实测
  反推，但平台翻页/限速会让速度前后不一致（实测过一个 60 条任务，中途估总时长偏高约 19%）。
- `--detach` 甩出去以后，**当前会话就管不着它了**：进度靠 `status`，停靠 `cancel`；
  机器重启/强制关机仍会中断它（已落盘的数据不受影响）。

## 8. 数据列名

七个平台叫法不一样（同是"点赞"，有 `liked_count`、`like_count`、`voteup_count`；
同是"发布时间"，有秒时间戳、毫秒时间戳、也有现成字符串）。做表/写脚本前先看
**`agent_crawler\列名对照表.md`**，里面按"帖子 / 评论 / 时间单位"分了三张对照表。
